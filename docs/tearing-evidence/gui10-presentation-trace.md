# GUI8 left-edge breakup trace (GUI10)

The committed JPEGs are AJ's 3.6.0-gui8 host-picker frame and connection-progress frame. Both show the same row-shaped left boundary. Frame A shows it on both toolkit displays while the picker is idle. Frame B shows the top progress page clean while the bottom page is mostly the prior/blank image, with only the left edge of current progress text visible.

## Candidate comparison

- `init_3ds()` calls `gfxInit(..., false)`, then disables double buffering on both displays before initializing the terminal consoles. Each toolkit `Screen` enables double buffering for its display at construction; every picker and progress screen reaches the same `runScreen()` or `runDualScreen()` presenter. The progress screen is `run_gui_call()`'s `GuiCallProgressScreen`, created after the worker starts. No worker-side display writes were found in that path. This ordering is not by itself evidence of a mismatched draw/present buffer.
- Toolkit rendering obtains the current draw pointer with `gfxGetFramebuffer()` at the start of every redraw. `setPixel()` maps logical `(x,y)` to `x * 240 + (239 - y)` and bounds-checks both coordinates; glyph blending uses the same bounds-checked pixel path. Fills are CPU pixel writes. No GX fill block or out-of-bounds first-column write was found that explains a row-aligned boundary on both displays.
- Each toolkit frame draws before presentation and calls `gfxScreenSwapBuffers()` once per participating display. The dual-screen path swaps TOP, then BOTTOM, then waits for VBlank; the progress path does the same for its TOP and BOTTOM pages. The installed libctru header warns against more than one swap per screen per frame, and these paths make one. This ordering does not identify a specific bad buffer, although the deferred TOP / BOTTOM wait boundary was not previously observable in AJ's frames.
- The direct framebuffer image copy and GPU display transfer belong to `N3dsRenderer`'s in-stream path. They are not called by the host picker or connection progress task, so changing their copy path would not be supported by these frames.

The images establish a presentation/buffer symptom, but do not expose the returned addresses or swap/VBlank timing needed to select one exact safe code fix. GUI10 therefore adds bounded records around each toolkit present. On AJ's 3DS, copy `sd:/3ds/moonlight/moonlight.log`; search for `UI_PRESENT` and `UI_PRESENT_VBLANK`. Each present records its screen, draw-buffer address, toolkit double-buffer state, flush-before-swap order, and whether its VBlank wait completed. A TOP record marked `vblank=deferred` is followed by the bottom present and its `UI_PRESENT_VBLANK` boundary record.
