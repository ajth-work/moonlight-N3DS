# GUI23.10 diagnostic log transfer

The client records a logical session across a startup segment, numbered routine segments, a durable critical journal and a small atomic metadata file. Physical sidecars are hidden from Check Logs. New recordings use metadata for fast inventory; re-entry is cached for 30 seconds, invalidated after sending or directory changes, with X to refresh.

The managed allowance is 8 MiB per session and 64 MiB across the SD logging directory, including mirrors. Startup is retained; at most 29 routine 256 KiB segments and a 64 KiB critical journal are kept. Monotonic record/segment sequences expose ordering; retired history sets gaps. Space for a frozen last segment and journal is reserved within the session allowance. Completed, closed and server-acknowledged recordings are eligible for quota cleanup; active/pending/legacy evidence is preserved. Existing legacy files can already exceed the budget: they are not silently destroyed. New recording is refused when the critical reserve cannot fit. This requires deliberate archival/cleanup; bounded metadata and the existing mirror may consume small additional overhead.

Uploads use the existing paired-client certificate and pinned Sunshine certificate. V2 negotiates at upload time and sends immutable, redacted captures in raw parts no larger than 240 KiB; the existing 256 KiB HTTP ceiling stays in force. Manifest size is bounded to 32 KiB, captures to 8 MiB/128 parts, responses to 1 KiB. Preparation and hashing stream through 16 KiB reads; there is no whole-session RAM buffer. Snapshot reads share the recorder lock, then recording can continue while frozen parts remain pinned.

The receiver durably acknowledges and hashes each part, reconstructs a resume bitmap after restart, verifies the ordered whole SHA-256, then records a final receipt. Only that receipt means transfer complete. Recording completeness is separate: a recording with retired history, an active snapshot, legacy uncertainty, or an unclean ending remains partial. An older v1-only Sunshine receives a bounded, explicitly partial snapshot. It cannot promise full recording delivery.

The upload worker leaves the main UI responsive. Separate bars show host-acknowledged content and the current HTTP request. Sending the final bytes is not displayed as final verification. B pauses and Check Logs / Send resumes from host acknowledgements. Failed or cancelled v2 captures retain their frozen sources. The immutable LOGCAP2 layout/redaction rules must be versioned if changed in a later release.

Sunshine keeps 20 completed logical captures per paired client and at most two incomplete captures; incomplete staging expires after seven days. Retention counts captures, not chunks. Verified assembly removes redundant parts. Logs are under the configured host app-data `moonlight-client-logs/<paired-client>/v2/<capture-id>/`, containing `session.log`, `manifest.json` and `receipt.json`. Existing v1 JSON files are unchanged.

Native portable checks: `sh tests/run_diagnostic_transfer_tests.sh` (C++17, OpenSSL development headers). The cross-project compatibility check additionally defines `HOST_RECEIVER_TEST`, supplies Sunshine's source root and nlohmann/json headers, and compiles using C++20 because the Sunshine header requires it. It exercises the actual client module against the actual receiver: multi-part transfer beyond 256 KiB, loss/retry/resume with immutable source prefixes, reused acknowledgements, redaction, final hashes, unclean partial recordings, corrupt local snapshots, logical inventory, cancellation, malformed responses and quota preservation. Sunshine's separate native tests cover mutual TLS/identity isolation, invalid schemas/paths/quotas, corrupt parts, out-of-order/duplicate parts and retention beyond 20 parts.

Hardware acceptance remains required. Confirm the final host receipt/hash/bytes and critical exit evidence. No renderer or PF algorithm change is included; this release does not claim to fix their latency/artifacts.
